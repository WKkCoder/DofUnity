# DNF 数据格式规格

对象:用户自备的游戏目录,里面有 `Script.pvf`、`ImagePacks2/*.npk`、`DNF.exe`。
本文只记录"怎么读"的事实、统计数字与来源,不包含从原版数据里解出的素材或脚本内容。
参考实现在 `tools/py/`(Python,标准库),每条事实标注证据编号,编号对应 [证据台账](evidence/ledger.md)。

状态标记:**已验证** = 在全部文件上跑通且结果吻合;**推断** = 根据形状与取值猜的,没有引擎里的原表;**未知** = 还没研究。

## PVF(Script.pvf)  已验证  E-001

- 头:`u32 guidLen(36)`、GUID、`u32 version(66282)`、`u32 dirTreeLen(27,112,312)`、`u32 dirTreeCrc`、`u32 nFiles(334,998)`。头长 = guidLen + 20 = 56。
- 解密(目录树与每个文件相同):按 32 位小端字,`out = ROR32(word ^ crc ^ 0x81A79011, 6)`。目录树用头里的 `dirTreeCrc`,文件用自己目录项里的 `crc`。
- 目录项:`u32 fileNo, u32 pathLen, path(latin1), u32 length, u32 crc, u32 relOffset`。
- 文件数据起点 = `headerLen + dirTreeLen + relOffset`,读取长度向上对齐到 4 字节,解密后截到 `length`。
- **校验规则**(E-011,由 `DNF.exe` 的 VA 0x011AB180 例程静态分析得出,在全库上成立):每个文件的 `crc` 既是解密密钥,也是校验值——对**解密后按 4 字节对齐的整段**(含末尾的对齐填充)做标准 CRC-32(多项式 0xEDB88320,即 `zlib.crc32`),种子取该目录项的 `fileNo`,结果等于 `crc`。全部 334,998 个文件通过(种子取 0 则 0 个通过;只算 `length` 字节则只有无填充的 81,053 个通过)。所有 253,945 个有填充的文件,解密后的填充字节全是零。
- 目录树同理:解密后的整段做 CRC-32,种子取 `nFiles`,结果等于头里的 `dirTreeCrc`。目录树解析完后剩的那 1 个字节是 `00`,是把目录树补齐到 4 字节倍数的填充(27,112,312 = 4 × 6,778,078),它也在校验范围内。
- 客户端的例程要求被校验的长度是 4 的倍数,否则直接判失败;校验失败时客户端记录错误并拒绝加载该文件。所以改动任何脚本后必须重算 `crc` 并用新 `crc` 重新加密,才能被原版客户端接受(这是对客户端行为的静态推断,没有运行验证)。
- 例程里另有一个全局变量(VA 0x01B08BC0,磁盘镜像里为 0)在非零时会被异或进密钥;它在全库上等效于 0,谁在运行时给它赋值**未知**。
- 以前误写成"`crc` 不是内容校验和":当时用的是 `[:length]` 的明文且种子取 0,两个条件都错了。
- **服务端符号印证**(E-018):用户服务器上的 `df_game_r` 带 DWARF,其中的打包库(`FilePack`)有名为"解密并校验 CRC-32"的函数,参数依次是种子、期望校验值、密钥、缓冲区、长度,与上面从客户端例程读出的用法一致;内存里的索引项有类型、名字、长度、对齐后长度、`crc`、偏移;打包库对象里的 `revision` 对应头里的 `version`(66282)。这是同一套打包库的另一份编译产物,客户端与它同源是推断,但接口含义与实测的数据完全吻合。
- 全库清单聚合哈希:`cb377e11645e024d9a3d775fdd613880bd520409382dbe961163878b65511154`(对清单里每个文件的十六进制 SHA-256,按目录顺序依次喂给 SHA-256)。
- 加速写法:把整段当一个大整数,逐字 XOR 与循环右移 6 位都用整数运算加掩码完成;335k 个文件解密加哈希约 2.7 秒(Python)。

文件类型:147,273 个标记流脚本(`B0 D0` 开头)、187,438 个 `.ani`(187,365 个二进制 + 73 个空文件或文本)、212 个 `.nut`(明文 Squirrel),其余是文本。

### stringtable.bin

`u32 count(395,044)`,随后 `count+1` 个 `u32` 偏移(相对第 4 字节),再往后是字符串池,字符串无终止符。第 i 个字符串 = `data[4 + off[i] : 4 + off[i+1]]`。池里既有 `[name]` 这样的标签,也有文本键、路径和 `[fixed]` 这样的关键字。

### 标记流脚本(`B0 D0`)  已验证  E-003

文件 = `B0 D0` + N 个 5 字节标记,标记 = `u8 类型 + i32 值`。147,273 个文件的正文长度全部能被 5 整除。

| 类型 | 含义 | 出现次数 |
|---|---|---|
| 2 | 整数 | 8,629,508 |
| 3 | 整数(只在 Unicode 范围表里见到) | 8 |
| 4 | 浮点(i32 位模式当 f32) | 127,854 |
| 5 | 标签,值是字符串池下标,字符串形如 `[name]` 或 `[/name]` | 3,815,867 |
| 6 | 括号词,如 `(UP)`、`(SKILL)` | 2,493 |
| 7 | 字符串或关键字,如路径、`[fixed]` | 2,726,904 |
| 8 | 分隔符 `,` | 1,721 |
| 9 + 10 | 总是成对:9 的字符串是 25 种固定值之一,10 的字符串是键(字符串引用) | 各 291,519 |

**服务端符号印证**(E-017):服务端二进制的 DWARF 里,脚本词法器的记号类型枚举共 12 项,与上表一一对应:0 结束、1 错误、2 十进制整数、3 十六进制整数、4 浮点、5 类型(即标签)、6 自定义数据(上表的"括号词")、7 字符串、8 连接符、9 整数对、10 字符串对、11 include(12 是上限)。类型 11 只出现在源文本词法器里,编译后的流里全库没有见到。上表的类型含义是之前仅凭字节形状推出的,现在有了独立来源。

tag 目录:全库 3,408 种开标签、3,232,710 次出现。前 10 个 25.73%,前 25 个 44.85%,前 50 个 61.91%,前 100 个 76.23%,前 200 个 87.63%,前 500 个 97.17%,前 1000 个 99.45%。
**标签语义未标注。** 工具 `tools/py/tag_catalog.py` 记录了每个标签后面紧跟的值类型形状。

战斗切片相关的 14 类扩展名(act、stk、ai、obj、atk、key、ptl、til、map、mob、skl、aic、dgn、apd)联合 1,596 种标签,前 100 个覆盖 70.95%,前 200 个 86.08%,前 300 个 93.20%。

## 二进制 .ani  已验证(语法)/ 推断(属性名)  E-004

187,365 个二进制 `.ani` 全部被下面的结构恰好读到文件末尾。

```
u16 frameCount, u16 imageCount
imageCount * (u32 len, bytes path)           # NPK 里的名字 = "sprite/" + path.lower()
u16 globalCount, globalCount * (u16 id + 负载)
frameCount * 帧:
    u16 boxCount, boxCount * (u16 boxType + 6 * i32)     # 14 = 伤害框(推断), 15 = 攻击框(推断)
    u16 imageIdx                                          # 0xFFFF = 无图
    若 imageIdx != 0xFFFF: u16 frameIdx
    i32 x, i32 y, u16 propCount, propCount * (u16 id + 负载)
```

- 全局属性(id: 负载字节数):0:1, 1:1, 3:2, 18:15, 28:2。
- 帧属性:1:1, 2:8, 7:8, 8:4, 9:4, 10:1, 12:4, 13:2, 16:字符串(u32 长度 + 内容), 17:0, 23:4, 24:2, 25:0, 26:4, 27:8;11 = 图形特效:`u16` 类型(0 到 6),类型 5 之后多 3 字节。
- 已核对取值:12 是延时毫秒;16 是音效键。13(伤害类型)与特效类型含义是**推断**。
- 帧属性 7、8、9、10、11(推断,证据 E-029、E-030):**7 = 图像缩放 (x, y)**(两个 f32;x 为负即水平镜像,(−1, 1) 是最常见的取值;镜像用原版截图核对过,其余缩放幅度未验证);**8 = 旋转角**(f32,弧度;围绕哪个点未知);**9 = 染色 RGBA**(4 字节;最常见 (255,255,255,170);**A 分量在叠加混合里被验证**,RGB 与像素相乘的方式未验证);**10 = 与下一帧插值的标志**(1 字节,取值 1 的帧 51,562 个、取值 0 的 82 个,分布在 14,470 个 `.ani` 里;带这个标志的相邻帧对里,染色 alpha 不同的占 33.7%,不带的只占 1.7%;**只验证了染色 alpha 做线性插值**,位置、缩放、旋转是否也插值未验证);**11 = 图形特效**(`u16` 类型,类型 5 之后多 3 字节):**类型 2 = 叠加混合(已用原版截图逐像素验证)**,类型 0、1、3、4、5、6 的含义未知。已实现:镜像、叠加混合、染色 alpha(含插值);其余都还没有实现。
- 全局属性 0 **很可能是"循环播放"**(推断,统计证据 E-025):多帧动画里,名字以 `stay/wait/move/walk/run/idle/stand/dash` 开头的 91.1% 带它,以 `attack/damage/die/down/cast/jump/throw` 开头的只有 2.3% 带它。不带它的动画不一定"只播一次"(特效由 `.act`/`.ptl` 等脚本决定怎么播),所以 `AniFile.Loops` 只回答"有没有这个属性",不替引擎做更多判断。
- 帧属性 25 与 26(推断,证据 E-039):**25(0 字节)= 循环起点,26(4 字节,有符号整数)= 循环终点与重复次数**。全库 153,097 个多帧二进制 `.ani` 里带 25 的 560 个、带 26 的 553 个,带 26 的全部也带 25,同一动画里 25 比 26 早出现的占 539/553;26 的取值以 99999、9999、999(大概表示不限)和 3、5、10、100(有限次)为主。本机数据没有文本格式的 `.ani`,所以这个命名不是本机证据,播放语义(次数是'再重复几次'还是'共播几次'、跳回哪一帧)没有对照。`Animator` 按这个假设实现:终点帧播完且还有次数时跳回最近的起点帧(没有就回第 0 帧)。全局属性 1 与名字没有相关(含义不明),全局属性 3、18、28 没有研究。
- 位置:精灵像素块左上角 = 世界位置 − 相机 + 帧的 (x, y) + IMG 帧头的 (x, y);坐标模型见证据 E-024。
- 镜像:水平镜像以物体的世界 x 为轴,像素块的左边缘 = 世界 x − 相机 x − (帧 x + 帧头 x + 像素块宽度);是否镜像 = 地图 `[NPC]` 里的朝向是 `[left]` XOR 该帧的 x 缩放为负(E-029)。
- 地图的 `[NPC]` 条目是 5 个值一组:NPC 编号、朝向字符串(`[left]` 或 `[right]`)、x、y、z。
- 地图的 `[animation]` 条目也是 5 个值一组:动画路径(相对地图所在目录,如 `map/elvengard/` + `Animation/GateBack.ani`)、图层名、x、y、z(E-030)。图层名在全库有 6 种:`[bottom]` 11,489 次、`[normal]` 11,301、`[closeback]` 10,095、`[middleback]` 4,362、`[close]` 3,671、`[distantback]` 2,722。精灵位置与 NPC 用同一个投影(E-024);网关地图里 `[closeback]`、`[normal]`、`[close]` 的位置与顺序(背景 < 光效 < 近景柱子)被原版截图验证,其余 3 种图层名的绘制顺序是**假定**(`[distantback]` < `[middleback]` < `[closeback]` < `[bottom]` < `[normal]` 与 NPC 按世界 y 排序 < `[close]`)。`[far/middle/near sight scroll]`(视差)在网关地图里没有,没有研究。
- 叠加混合(图形特效类型 2,E-030):`目标 = min(255, round(目标 + 源.rgb × 源.a/255 × 染色alpha/255))`,只在最后四舍五入一次(整数形式 `(2N + 65025) / (2 × 65025)`,`N = 目标 × 65025 + 源 × 源.a × 染色alpha`)。画面里的光效 alpha 随时间在 `.ani` 帧之间线性变化(帧属性 10),一帧的延时没有给出时按 0 毫秒算(最后一帧只是终点关键帧)。
- 路径里可能带 `%02d%02d` 这类占位符,运行时由装备编号替换,替换规则**未研究**。
- 端到端核对:两个 `.ani` 指到对应 IMG 帧后拼出连贯动画(4 帧枪口火焰各 60 毫秒;1 帧蜥蜴人受击)。

## NPK 与 IMG v2  已验证  E-002

- NPK:`NeoplePack_Bill\0`(16 字节)+ `u32 count` + `count * 264` 字节目录项:`u32 offset, u32 size, 256 字节名称`。名称与固定密钥逐字节异或,密钥 = `("puchikon@neople dungeon and fighter " + "DNF" * 100)[:255] + "\0"`。
- 全部 1,575 个 NPK、80,464 个条目 = 80,328 个 IMG v2 + 136 个旧版 `Neople Image File`(旧版**未解析**)。
- 49 个 IMG 名称在两个 NPK 里重复(39 个内容相同,10 个不同);引擎的覆盖顺序**未知**。
- IMG v2:32 字节头 = 16 字节魔数 + `i64 indexSize` + `i32 version(2)` + `i32 frameCount`。索引项:链接帧 8 字节(`i32 0x11, i32 target`),其他帧 36 字节(`i32 type, compress, w, h, size, x, y, frameW, frameH`)。帧数据从 `32 + indexSize` 开始,按索引顺序紧挨着。
- 像素格式:`0x0E` ARGB1555、`0x0F` ARGB4444、`0x10` ARGB8888;`0x11` 链接帧。压缩:5 未压缩、6 zlib。
- **帧数据长度的坑**:`compress=6` 时 `size` 是压缩后长度;`compress=5` 时实际长度是 `w*h*bpp`,而 16 位格式的 `size` 字段按 32 位记,直接用它推进偏移会让 901 个 IMG 整体错位。
- 例外:97 个 1×1 占位帧(类型 `0x0E`、`compress=6`、`size=4`)的 zlib 流被截断,按透明像素处理。
- 全量扫描:80,328 个 IMG 布局全部吻合;非链接帧 9,860,808 个,其中 9,860,711 个解压后长度恰好等于 `w*h*bpp`;链接帧 1,893,540 个全部在 16 跳内落到真实帧。
- 体量:解压后 40.98 GB,压缩态 3.54 GB,所以必须按需解码。
- 颜色转换:4444 每通道 ×17;1555 每通道 `round(v*255/31)`,即 `(v*255+15)/31`,A 位为 1 时不透明。1555 的规则用原版客户端的屏幕输出校验过(E-023):位复制 `(v<<3)|(v>>2)` 在 v=3、7、24、28 上差 1,会让 12% 到 36% 的像素与原版不同,不能用。4444 还没有被屏幕样本覆盖(全库只有 7,800 帧),按同样的"归一化后四舍五入"理解,尚待验证。
- 混合方式(叠加等)来自 `.ani` 的图形特效属性,不在 IMG 里;叠加的规则与验证见上面 `.ani` 一节和 E-030。

## DNF.exe(静态,磁盘字节)  E-005、E-006

见证据台账。要点:PE32 x86,41,978,368 字节,时间戳 2021-03-19 16:02:58 UTC;9 个同名 `nsn` 节(`XRW`,其中 #7 为 `XR`)、`.idata`、`.rsrc`;入口点在第 0 个 `nsn` 节。
Ghidra 的自动分析已完成(E-007、E-010):第 0 个 `nsn` 节 87.69% 的字节被反汇编成指令、有 48,013 个函数,**确实是明文 x86 代码**;第 3 个 `nsn` 节约一半是明文代码(41,934 个很短的函数),其余没有被反汇编,取样的 12 处都是夹着无意义指令的变形 x86 代码,不是数据(E-044,修正了 E-005b 的猜测);第 7 个 `nsn` 节(3.2 MiB,熵 7.94)被解成指令的字节不到 0.1%,不是可直接反汇编的代码。
**这些不是对运行行为的观察。** 保护层(`TerSafe`、`nsn` 节、`.rsrc` 里的 `FILE` 与 `HSH` 资源)的作用**未知**,碰它之前必须先问用户。

## 客户端里的字符串数据块  已验证(解码结果可读)/ 推断(格式由汇编读出)  E-041

`DNF.exe` 里的界面文字、资源路径、脚本接口名、`[标签]` 名都不是明文。每处用到文字的地方把一个"数据块"的地址压栈,调用访问函数(宽字符版 VA `0x0119FEF0`、窄字符版 `0x0119FED0`),拿回一个指向已解码文字的指针(解码结果缓存在哈希表里)。

块的布局(小端):

| 偏移 | 大小 | 含义 |
|---|---|---|
| 0 | 1 | 标志:窄字符版第 0 字节为 `A1` 表示明文;宽字符版从偏移 0 起的 2 字节为 `A1 2C` 表示明文(明文块后面直接是以 0 结尾的字符串) |
| 1 | 1 | `b1`(已编码的块用它);令 `m = b1 AND 0xFE` |
| 2 | 2 | 长度字段(u16);**字符数** = `((m << 7) OR m) XOR 长度字段` |
| 4 | 字符数 × 单位 | 正文;宽字符版单位 2 字节(UTF-16LE),窄字符版单位 1 字节;含结尾的 0 |

解码:`key = m OR 0x9A714CA0`(32 位)。正文按 4 字节小端字依次处理:`out = word XOR key`,然后 `key = key × 0x1003F + out`(模 2³²)。末尾不足 4 字节的部分按字节:`out = byte XOR (key & 0xFF)`,然后 `key = key × 0x107 + out`。`out` 序列就是明文。

全库验证:`tools/py/decode_strings.py` 在 18,055 个不同的数据块上解出 18,039 个可打印文本,没有解错的;"明文"标志的块一个也没有出现。这只是读文字的办法,不碰保护层,也没有运行游戏。
