# 怪物出招决策与默认 AI(M14,E-100、E-101、E-102)

没有 `[ai pattern]` 的怪物(演示房间里的怪物就是)走客户端 C++ 里的默认 AI。本文只记**机制、常数与实现结构**;`.mob` 里的具体数值(射程、概率、延迟等)是原版数据,不进仓库。

证据等级:函数结构与常数来自静态读码(各函数的汇编逐条读过,高);哪些函数在整体里扮演什么角色、控制器指针的偏移是按引用分布与调用形状推断的(中);基础攻击怎么触发、被动怪物何时转为主动、移动的停走节拍**没有读通**(低),实现里用占位代替并单独标出。没有运行客户端,也没有拿原版录像校准出招节奏。

## 1. `[attack kind]` 记录(E-100)

- `.mob` 的 `[attack kind]` 由加载函数 0x012b00be 读入:每 12 个数一条记录,第 i 条对应第 i 个 `[attack motion]`(和同下标的 `[attack info]`)。
- 十二个数依次是(命名是我们自己起的):

| 序 | 含义 | 序 | 含义 |
|---|---|---|---|
| t0 | 站在射程里时的出招概率(%) | t6 | 背面射程 |
| t1 | 不论远近的出招概率(%) | t7 | 右侧死区 |
| t2 | 目标是非角色对象时的概率(%) | t8 | 朝 −y 的射程 |
| t3 | 初始"可用"标志 | t9 | −y 侧死区 |
| t4 | 正面射程 | t10 | 朝 +y 的射程 |
| t5 | 左侧死区 | t11 | +y 侧死区 |

- "对倒地目标出招的概率"不在这十二个数里,记录构造时是 0,只有单独的 `[attack down prob]` 会改;所以缺省时怪物不会对倒地的目标出招。
- 全库结构检查(`dnf mob-check`,现在是门槛):约三分之一的怪物脚本带这个标签;每个文件的数的个数都是 12 的倍数、三个概率都在 0 到 100、四个射程都不为负——和上面的读法相符。约五分之四的记录有可用的射程范围,其余射程全为 0;约百分之三的文件记录条数与动作个数对不上(决策只用两边都有的下标)。

## 2. 出招决策(E-101)

决策函数 0x0088d7a0,"这一招现在能不能用"0x00882510,"目标在不在射程里"0x00881e50:

1. **只在状态 0 时决策**——状态 0 是站立(`STATE_STAND`),走路也算在内(客户端没有"走路"状态,§7),所以怪物边走边抽签、不必先停下(E-148;此前误读成"只在站着时")。怪物自己的时钟(出生以来的毫秒数)不到 3000 就不决策(这个限制只对队伍号不在 0 到 11 之间的对象生效,怪物属于这一类)。
2. 到点后**先定下一次的时刻**:现在 + 抖动 + `[attack delay]`,抖动 = rand % 范围 − 范围 / 2,范围 = (int)(delay × 0.2f)(所以是 ±10%);不管这次出不出招。
3. 在"已准备好且能用"的记录里**随机挑一条**(rand % 个数),以状态 8、数据 [记录下标] 请求状态切换;一条都没有就这次不出招。
4. **能不能用**:逐个敌对的角色目标——在射程里 → 过倒地门槛(目标倒地时按"对倒地目标"的概率掷骰) → 按 t0 掷骰,中了就能用;所有目标都没通过时,**无条件**再按 t1 掷一次(与有没有目标无关)。
5. **掷骰** = `rand % 10000 < 概率 × 100.0f`(单精度比较)。
6. **射程**:朝左时背面是 +x、朝向右时相反;横向要求目标位置(两侧各放宽目标宽度的四分之一,整数除法)落在背面射程到正面射程之间,且不在左右死区的开区间里(两个死区是绝对的左右,不随朝向镜像);纵向同理(放宽目标进深的四分之一)。正面与背面射程全为 0、或两个纵向射程全为 0 时直接回答"不在"。
7. **敌对放大**:怪物进入主动出击的状态(模式 9、10,0x0088a6e0)时,每条记录的 t0 概率乘 1.3;重复进入是否叠加、离开是否还原没读。
8. 随机数是客户端的 rand(0x00E50E60,种子指针为空,原版里不可复现);我们用确定性的 `ClientRandom`,每只怪物一个由房间种子派生的状态。

## 3. 我们的实现

| 部分 | 位置 | 内容 |
|---|---|---|
| 记录与规则 | `Dnf.Game`:`AttackKindRecord`、`MonsterAttackRules` | 十二个数的解析、射程判断、掷骰、下一次决策时刻——纯函数 |
| 决策器 | `Dnf.Play`:`MonsterAttackChooser` | 每只怪物一个:持有各记录的"已准备/停用"状态、敌对放大、`Decide`(定时抽签)、`AnyInRange` |
| 接线 | `MonsterActor.SetAttackKinds`、`RoomCombatSession.Create` | 记录条数多于动作的条目停用;挑了第 i 条就放第 i 个出招动画与第 i 个攻击信息(`AttackIndex`、`SetStrikes`);命中停顿期间怪物时钟不走 |
| 走位规则 | `Dnf.Game`:`MonsterMoveRules`、`MonsterMoveMode`、`MonsterTempo` | 距离与视野、防撞边、格子比较、远程取距、倒着走、模式的节拍与停下概率表——纯函数(§7) |
| 走位大脑 | `Dnf.Play`:`MonsterBrain`、`MonsterBrainTraits` | 每只怪物一个:目标维护、发现迟滞、模式机(游荡、敌对、绕背、追击、迟疑、站桩、靠近、反向)、到点选方向、受击与打中主角与被挡住的通知;`For` 按 .mob 的类别决定用不用并把类别带进大脑(§7) |
| 走位接线 | `MonsterActor.SetDefaultAi`、`ThinkWithBrain`、`Blocker`;`RoomCombatSession.Create` | 先让大脑推进,再按 §2 决策出招(站着或走着都决策),不出招就按大脑选的方向走;怪物步速 = `[move speed]` × 0.1573;关着的出口门体怪物也走不进去;走路时位置一秒没变就通知大脑(`TrackStuck`);靠近模式里强悍与凶猛类别带霸体 |
| 旧占位 | `MonsterActor.Think` 的另一支 | 没有 `[attack kind]` 的怪物、一招动画都没有的怪物仍走旧的"够得着就出招 + 冷却";没有走位大脑的怪物(脚本指挥的、`[oneside move]`)仍是视野框 + 直线追击 |

**推断与假设(都在代码里单独标出,不要当成原版行为):**

- **射程全为 0 的记录**(有的基础攻击这样写)在客户端里靠什么触发没读到。我们用调用方给的几何判断代替"站在射程里":第 0 招的攻击框够得着主角的受击框(没有受击框时用固定射程),够得着就算能用、**不掷骰**(Z1 规则);第 0 招以外的全 0 记录只剩"不论远近"那一次掷骰。
- 有走位大脑的怪物按模式机进入敌对状态(§7:发现后约 0.7 秒的迟滞是基线里的经验值);没有的仍是"看到主角(占位视野)就进入敌对"。
- 记录的可用标志不清除,也不按 `[cooltime]` 恢复。
- 没有走位大脑的怪物移动仍是占位:直线走到某条可用记录够得着为止,最近停在最小间隔之外;有走位大脑的怪物见 §7(有停走节拍、格子比较与 `[warlike]` 倒走,没有 A* 寻路)。

效果(真实数据,`combat-check --trace`):怪物出生满 3 秒才第一次出招,之后每隔一个 `[attack delay]` 加抖动出招一次;此前的占位是进入射程就出招。

## 4. 默认 AI 的整体结构(E-102)

- **两套机制并存**:(A) 新式控制器——怪物对象里的 `ai` 指针(`+0x50f4`;对没有脚本的怪物它不触发出招,但会给出移动的目的地);(B) 旧式模式机(对象 `+0x388c`):0x008822b0 的更新函数每 333 毫秒调模式更新 0x0088d270,移动节拍 0x00889da0(每个模式一张时间表 0x015ce7c0、停下概率数组 0x015ce9a0),方向选择 0x0088ab90(带格子寻路,`[warlike]` 决定"倒着走"的概率),待机选择器 0x00891650,出招抽签 0x0088d7a0。
- 模式的类别号:12 `[melee combat]`、13 `[range combat]`、14 `[close-passive]`、15 `[close-carefully]`、17 `[close-tough]`、23 `[goblin]`(只是事件地精的行为)、26 `[fixture]`、27 `[stay]`。
- 基类里其余会请求 STATE_ATTACK 的位置:0x0088f4f0(特殊攻击)、0x0088d080(触发表)、0x00890550(投掷函数,见 `docs/monster-projectile.md`;M15 更正:原记为“召唤表”)、0x0089c7b0(受击回调,含 `[counter attack]`)、0x008680c0(没分析);它们都不是普通基础攻击的触发。
- **更正**:E-086 与旧版 `docs/hit-pipeline.md` 写的"控制器指针在 `+0x58bc`"与引用分布对不上(`+0x58bc` 的引用集中在 0x0083 一带的另一个类),改记 `+0x50f4`。

## 5. 没读通 / 没做

1. 射程全 0 的基础攻击的真实触发(最大的缺口)。
2. 模式机里没做的(§7):被打中后叫同伴一起靠近(0x0088f170)、各模式的速度倍率数组(读不到消费者,速度保持中性)、靠近终点的可走区校验(`+0xe4` 号虚函数)、多目标打分;被动类别、绕背、追击、10 秒超时与再接战、远程怪物边走边出招都已读通并接上(E-148)。
3. A* 寻路的平局规则(0x0112e4c0)。
4. 记录可用标志的清除与 `[cooltime]` 恢复。
5. `[throw attack]` 的投射物已在 M15 接上(`docs/monster-projectile.md`);其飞行的运行时语义(速度单位、`[move variable 1]` 两个数、sin/cos、重力、落地)是推断。
6. 主角倒地状态(主角还不会躺下,倒地门槛没有用武之地)。
7. 敌对放大是否叠加、是否还原;命中停顿期间原版是否暂停怪物时钟。
8. 0x008680c0 没分析。

## 7. 走位:模式机(M22,E-114;M54 补全,E-148)

走位取自旧式模式机(§4 的 (B)),枚举值就是客户端的模式号(`MonsterMoveMode`):1 迟疑、4 追击、9 敌对·近战、10 敌对·远程、11 绕背冲刺、12 靠近、13 游荡、15 站桩、21 反向。规则与常数在 `MonsterMoveRules`(纯函数),状态在 `MonsterBrain`(每只怪物一个,随机数是每只怪物各一个的 `ClientRandom` 状态)。服务端没有怪物 AI 的代码(只管掉落与物品),这套模式机是客户端算的(主机客户端算,其余客户端收同步)。

**模式机在哪**(静态读码,Capstone 与 Ghidra 无头脚本只读 `DNF.exe` 普通代码段,非 REA):怪物基类的虚表在 `0x0170be64`,用到的槽——设方向 `0x0088a0a0`(`+0x604`)、换模式 `0x00880910`(`+0x778`)、离开模式 `0x00894fb0`(`+0x770`)、进入模式 `0x0088a6e0`(`+0x774`)、模式更新 `0x0088d270`(`+0x76c`)、移动节拍 `0x00889da0`(`+0x7f8`)、绕背 `0x0088b410`(`+0x79c`)、靠近 `0x0089dd20`(`+0x7a0`)、叫同伴 `0x0088f170`(`+0x84c`)、目标是否有效 `0x0088a240`(`+0x58c`)、每帧更新 `0x008822b0`(`+0x818`)、出招决策 `0x0088d7a0`(`+0x820`)、卡住检测 `0x0088a4c0`(`+0x81c`)、找目标 `0x0089e170`(`+0x828`)、发目标包 `0x00880760`(`+0x838`)、设目标 `0x00880c80`(`+0x7bc`)、取状态 `0x0067e810`(`+0xb8`)、方向选择器 `0x00891650`(`+0x7c0`);另有回包处理 `0x0088b270`、受击回调 `0x0089c7b0`、打中主角 `0x00892880`。类别号(服务端 `initObjectCategory` 的顺序):12 近战、13 远程、14 被动、15 谨慎、16 全程霸体、17 强悍、18 凶猛、19 单向移动、26 摆设、27 站桩。

**状态枚举里没有"走路"**:`STATE_STAND`(0)就包含走路,`STATE_JUMP` 是 6。出招决策与移动节拍都在状态 0 里跑(节拍在状态 6 里也跑),模式更新与节拍在状态 3、4、5、8、9(受击、倒地、死亡、出招等)里挂起。所以**怪物边走边出招,不必先停下**;E-114 以前把决策写成"只在站着时"是误读(E-148 更正)。

**一帧的流程**(0x008822b0;`MonsterBrain.Update`):

1. 出生在模式 13(0x0088b350)。
2. **维护目标**:有目标时它失效(跑出视野)就当即放弃;没有目标时,从"上一次设置目标"算起至少隔 1000 毫秒才找一次(出生后第一次立刻找)。主角在 `[sight]` × 1.4 之内算有效目标(`[sight]` 没写取 200,写 0 表示无限远);距离里纵向差先除以 0.29 取整、再与横向差求平方和的平方根(0x0088a240、0x007fb7c0)。
3. **发现之后进入敌对**:客户端是把"目标改变"发给服务器、再从回包里进入下一步(0x0088b270 是回包处理函数),所以中间有一段时延,时延本身没读到;我们按基线连拍里量到的约 0.7 秒迟滞做(`MonsterBrain.NoticeDelayMs`,非 REA 的经验值,一个样本)。回包处理先试绕背(0x0088b410:掷骰 50%,有目标,而且没有 `[range combat]`),成了进模式 11,否则 `[melee combat]` 进 9、再不然 `[range combat]` 进 10。**挨打不加快发现**:客户端有个"受击后立刻找目标"的开关,没有任何怪物数据写它(E-114 以前以为挨打会跳过间隔与迟滞,更正)。
4. **模式更新**(0x0088d270,每 333 毫秒一次,状态 3、4、5、8、9 里挂起),各模式:
   - 敌对 9、10:进入满 10001 毫秒回游荡 13。**回游荡之后不会自动再接战**——接战只发生在"目标改变"的回包里(找到新目标、目标丢了又找到、或者被远处打中后靠近到位),模式开始时刻只由进入函数写(0x0088a718),攻击与受击都不重置它。所以站着不动的主角在头 10 秒之后挨打很少。
   - 绕背 11:没目标回游荡;冲过终点(朝左走的已经不在终点右边、朝右走的已经不在终点左边)转 9(近战)或 10(远程)。
   - 靠近 12:没目标满 5 秒回游荡;有有效目标时,近战怪物把终点改成目标当前的位置、纯远程怪物转迟疑 1。
   - 追击 4:没目标回游荡。迟疑 1:没目标转站桩 15。反向 21:满 501 毫秒转追击 4。
   - 游荡、站桩里没有自动转换(只有一条:怪物对象里某个类型字段为 1 或 2 时转巡逻模式 27 或 28,字段的来源没读,没接)。
5. **移动节拍**(0x00889da0,表 0x015ce7c0):到点才重新选方向并排下一次——间隔 = 基数 + 随机数 % 范围,走着与站着各一组:游荡、站桩、反向 走 500 + %1000、站 300 + %3000;敌对、绕背、靠近 走 1000 + %300、站 800 + %200;追击 走 1000 + %1000、站 300 + %3000;迟疑 走与站都是 300 + %3000。选好之后按停下概率(表 0x015ce9a0)取消方向:横向都是 0,纵向游荡 50%、追击与迟疑 30%、其余 0。选定的方向一直走到下一次选择,所以怪物不是每帧朝主角校正,会冲过头再折回来。方向选择里换了模式时(目标没了回游荡、靠近到位转敌对),外层照旧用选出的方向与"新模式"的节拍表、停下表往下走。
6. **方向选择**(0x00891650,switch 的标号是模式号减 1):
   - 游荡:40% 的几率去走;先看防撞边(离房间两边不到 80 像素就朝里走),否则横向随机左右;纵向随机上下(再被停下概率砍掉一半)。
   - 近战敌对(0x0088ab90 在没有障碍时的结果):比较自己与目标所在的格子(横向每 16 像素、纵向每 12 像素一格),横纵各自朝目标那一格走,同格就不动;然后"倒着走"判断:`好战度加成 + [warlike] ≤ rand % 100` 就把两个方向取反。好战度加成只有敌对模式(9、10)是 50(进入时设、离开时清,0x0088a6e0、0x00894fb0),所以 `[warlike]` ≥ 50 的怪物在敌对里永远不倒着走,而追击与迟疑里(加成 0)`[warlike]` 为 50 的怪物有一半的选择背对主角。
   - 远程敌对(模式 10):横向与主角保持距离——距离 ≥ 视野 × 0.9 靠近、≤ 视野 × 0.5 后退、之间不动;纵向永远朝主角那一行走(从不选"不动")。因为出招决策只要求状态 0、而走路就是状态 0,远程怪物是边走边出招的;E-114 里"读码自相矛盾"的说法是误读,更正。
   - 绕背 11:横向朝目标当前的 x 走,纵向不动;终点是目标 x 加或减 视野 × 0.5(怪物在目标左边就取加,浮点结果截断)。
   - 追击 4:80% 的几率朝目标走(同样先看防撞边),其余站着。迟疑 1:先看防撞边,不在边上才有 30% 的几率朝目标走。两者的"朝目标走"就是上面的格子比较。
   - 靠近 12:横向、纵向各自朝终点走,离终点不到 `宽度/2 + 10`(`[width]` 的第一个数)的那一轴不动;两轴都到了、或者离目标不到 `max(70, 视野 × 0.1)`,就算到了:被动与谨慎类别回游荡,其余再试一次绕背、不绕就按类别进 9 或 10。
   - 反向 21:把当前的两个方向取反。
   - 站桩 15:不走。
7. **受击与打中主角**:绕背里挨了打转追击(0x0089c7b0);攻击者是主角、离自己不近(距离 ≥ 150)而且还不在靠近中,就进靠近模式 12(0x0089dd20)——进入时视野 × 1.5(离开时乘 1/1.5 取整还原),强悍与凶猛类别(没有全程霸体的)带霸体;终点按类别:强悍与没写类别的直奔目标所在,凶猛停在目标靠自己这一侧、横向差五分之一处、纵向偏 50,被动与谨慎在目标左右随机一侧、与自己横向差一半处、纵向再随机偏一点(终点横坐标夹进房间)。冲刺或靠近途中打中了主角转追击(0x00892880)。
8. **卡住**(0x0088a4c0):走路的动作里、状态 0、整数位置一秒没变,转反向 21(掉头走 501 毫秒)然后追击 4。我们的接法在 `MonsterActor.TrackStuck`:位置变了、不在走路相位、或者两次思考隔得久(中间出过招、受过击)都重新计时。
9. **进入与离开敌对**:进入时好战度加成设为 50、出招概率乘 1.3(§2);离开时客户端乘约 1/1.3,我们直接还原(`MonsterAttackChooser.LeaveHostile`)。绕背、靠近、追击不算敌对。

**哪些怪物用大脑**(`MonsterBrain.For`):有 `[melee combat]` 或 `[range combat]` 的走对应的大脑(类别与 `[width]` 带进大脑:近战或远程、被动、谨慎、强悍、凶猛、全程霸体);`[stay]` 的是原地不动的大脑(不找目标、不走、不抽签、对一切通知无动于衷);`[oneside move]`、没有这几个类别的怪物(行为由 .ai 脚本指挥,见 §8)仍走旧占位。全库 2070 个 .mob 里,带 `[melee combat]` 的 882 个、带 `[range combat]` 的 236 个(汇总数,本机脚本扫描,非 REA;两个类别可以同时出现)。

**步速**:`WalkSpeed` 不再按主角的步速折算,改成 `[move speed]` × 0.1573 像素/秒(`MonsterTuning.WalkPixelsPerStat`)。这是基线连拍(S09b,不新录)里一只怪物匀速走向主角的线性回归斜率除以它的 `[move speed]`——**非 REA 的测量、一个样本、线性关系是假设**。各模式的"速度倍率数组"(进入模式时写 +倍率、离开时写 −倍率到控制对象,绕背与敌对 100、对强悍与凶猛的靠近 200)读不到谁消费它,速度保持中性。

**障碍与可走区**:关着的出口门体怪物也走不进去(`MonsterActor.Blocker`,与主角共用障碍表,每帧由房间会话从主角身上取);已经压在障碍里的怪物(出生点落在门体上)不受它挡,免得出不来。出生点落在可走区之外的怪物(首领从屏幕外登场的常见情形):脚本驱动的与走位大脑驱动的可以不受可走区限制、走到区里为止(M54 起,此前只有脚本怪物;推断,与 E-128 一致);没有这两种驱动的旧式怪物原地不动。

**没读通 / 推断**(代码里都单独标了):

- 各模式的速度倍率数组的消费者、叫同伴(0x0088f170,被打中后 70% 的几率叫附近的同伴也去靠近)、靠近终点的可走区校验(`+0xe4` 号虚函数)、多目标打分、寻路的平局规则(0x0112e4c0)、`[vision]` 与 `[fixture]` 的含义、"目标改变"回包的时延来源——没做或没读。
- 零射程攻击记录的真实触发(§5 第 1 条)。
- "头 10 秒之后不再自动接战"是读码结论(模式开始时刻只有进入函数写);回包是否会被服务器周期性地再发没有证据(服务端没有怪物 AI 的代码)。
- **站着不动的主角多久挨第一下**:方向每 1.0 到 1.3 秒才校正一次、目标格只有 16 像素宽,怪物容易在目标格两侧来回冲过头,碰巧在决策时刻落进同一格才会站定出招;E-148 以后怪物走着也出招,冲过头不再是障碍。基线 S09b 里有一个样本约 5.6 秒(非 REA)。
- 0.7 秒迟滞与步速斜率都只有一个样本。

## 8. 带 `[ai pattern]` 的怪物:由 `.ai` 脚本驱动(M36,E-128)

前面 1 到 7 节是**没有** `[ai pattern]` 的怪物走的默认 AI;全库 1,956 个怪物里有 1,232 个带 `[ai pattern]`,它们的出招与走位由四个 `.ai` 脚本(事件、选目的地、动作、移动方式)决定,运行时在 `Dnf.Play.MonsterScript`(求值器在 `Dnf.Game.Ai`),读法见 [`docs/ai-script.md`](ai-script.md) 的"怎样用"一节,整个里程碑见 [`docs/flow.md`](flow.md) 第 22 节。

- 两条路径互不混用:`MonsterActor` 有脚本就走 `ThinkScripted`(思考节拍、冷却、目的地全按脚本),没有脚本仍走本文的默认 AI;老用例(单元测试里依赖"站在可走区域之外就被冻住"的几条)只在既无脚本也没有走位大脑的怪物上成立,脚本怪物与大脑怪物在可走区域之外时允许走回来。
- 默认 AI 的模式机(§7)对脚本怪物不存在:脚本直接给出"这次出哪一招""往哪走",没有模式号;所以 §5 与 §7 列的没做项只影响没有脚本的那 724 个怪物。
- 脚本怪物的受击框只来自动画帧里的 `[DAMAGE BOX]`;没有框的状态打不到,所有动画都没有框的怪物永远打不到(自动机与清房条件都跳过它们)。


## 9. 脚本怪物的出招:`.act` 触发器与被动对象(M36-4,E-130)

第 8 节里脚本只决定"出哪一招""往哪走";招式本身的 `.act` 里还有触发器:到指定帧放出被动对象(飞行物、地面范围、陷阱)、改自己的速度、朝向、帧与出招。这些现在由 `Dnf.Game.Act.ActRunner` 运行、宿主在 `MonsterActor` 与 `RoomCombat`(见 [`docs/act-script.md`](act-script.md) 末尾与 [`docs/flow.md`](flow.md) §24)。对主角的伤害用主角的受击框和被动对象自己的攻击信息;怪物打主角一侧的新伤害路径仍是旧占位。没做的触发器(`[IF]`、`[IS IN POS]`、`[LOAD TARGET]` 等)不会触发,所以带它们的招式只会少放一部分对象,不会出错。
