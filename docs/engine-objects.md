# 引擎里的对象:类层次与种类码

客户端 `DNF.exe` 里,游戏对象(角色、怪物、被动对象、陷阱等)是一棵很大的 C++ 类继承树。`.act` 动作脚本、`.ai`、`.mob` 里的"对象种类"(`[IS OBJECT TYPE]`、`[WHICH] [MONSTER]`……)最后都落到这棵树上。
本文只记**结构事实**(地址、种类码、继承关系、虚函数槽的含义),都是对 `DNF.exe` 磁盘字节与反汇编的静态读取结果;类的真名读不到(见下),下面的名字是我们自己起的。证据见 `docs/evidence/ledger.md` 的 E-051。

## 怎么读出来的

- 客户端的类型描述符(`type_info`)共 3,227 个,**类名被抹掉了**:名字只剩一个 "." 和两个字节的编号,所以不能靠名字认类。
- 但 `__RTDynamicCast` 要用的结构(完整对象定位器 → 类层次描述符 → 基类数组)是完整的:4,532 个定位器,3,065 个类有"主虚表"。`tools/py/rtti_scan.py` 从磁盘字节恢复出每个类的基类链、虚表地址、槽数,以及虚表里"只返回常量"的小函数的常量值;输出在本机 `re/notes/rtti_classes.tsv`(不入库)。
- 脚本动作里的 `dynamicCast(对象, 0, 基类描述符, 目标类描述符, 0)` 里的"目标类描述符"地址,就是下表第一列。
- **种类码**不是类的常量,而是每个对象实例里的一个字段(偏移 `+0x90`);所有类共用同一个读取函数(槽 `0x34`:返回 `+0x90`)。每一层的构造函数会调用一个"初始化函数",把种类码写成自己的值。
  由"哪个构造函数调用了哪个写种类码的初始化函数"即可知道类与种类码的对应(下表第四列)。

- 依附体(buff/debuff)是另一棵树:`0x019d97e8`(41 槽)与它的子类 `0x019d9958`(45 槽),与上面的对象树无关(只共享一个接口式基类 `0x019d91ac`)。

## 与脚本关键字的对应

- `[IS OBJECT TYPE]`(`.act` 条件 0x16)**不做 `dynamicCast`**,而是比较槽 `0x34` 返回的种类码:`[COLLISION OBJECT]` ⇒ 种类码等于 1;`[ACTIVE OBJECT]` ⇒ `0x11`;`[CHARACTER]` ⇒ `0x111`;`[MONSTER]` ⇒ `0x211`;`[PASSIVE OBJECT]` ⇒ `0x21`;`[TRAP]` ⇒ `0x221`;`[BREAKABLE]` ⇒ `0x421`;`[AI CHARACTER]` ⇒ 槽 `0x38` 返回非 0。**是"相等",不是"继承":一个怪物(0x211)不满足 `[ACTIVE OBJECT]`。**
  槽 `0x38` 在多数类里是常量"假";`Character` 里读字段 `+0x551d`(非 0 即真),所以它表示"这个角色是 AI 控制的"。
- `[WHICH]` 的 `[CHARACTER]`、`[MONSTER]`、`[PASSIVE]` 三个选择器用同样的种类码(`0x111`、`0x211`、`0x21`)筛选对象管理器里的对象;`[AI CHARACTER]` 用槽 `0x38`。
- `[IS INDEX]`(`.act` 条件 0x19/0x1a)依次尝试三种类:`Monster`(读字段 `+0x254`)、`PassiveObject`(读字段 `+0xd64`)、`Character` 的那个子类(调槽 `0x40`),取第一个能转换的类做比较。槽 `0x40`(`getObjectIndex`)在各类的实现:`CollisionObject`/`ActiveObject`/`Monster` 共用"读 `+0x254`";`PassiveObject` 读 `+0xd64`;`Character` 读 `+0x3c08`;`Character` 的那个子类用一个读 `+0x5668` 一带的函数。

## 命中相关的虚槽(详见 [hit-pipeline.md](hit-pipeline.md),证据 E-057)

槽位移(字节):`+0x2b0` 命中判定 `tryHit`、`+0x2b4` 碰撞盒几何、`+0x2c4`/`+0x2c8` 本地命中钩子(攻击方/受击方)、
`+0x2cc`/`+0x2d0`/`+0x2d4` 攻击方的 BeforeAttack/Attack/AfterAttack、`+0x2d8`/`+0x2dc`/`+0x2e0` 受击方的 BeforeDamage/Damage/AfterDamage、
`+0x210`/`+0x214` 命中登记(是否已命中过、登记表地址)、`+0x230` 解析"实际对象"、`+0x328`/`+0x32c` 根所有者/所属者、`+0x37c` 是否可被打、`+0x388` 受击反应、`+0x398`/`+0x39c`/`+0x3a0` 受击反馈/stuck 特效/硬直毫秒与模式、
`+0x2a0`/`+0x2a4`/`+0x2a8`/`+0x500` 是 `setHp`/`getHp`/`getHpMax`/`isDead`。六个核心类各槽的实现地址由 `tools/py/vslots.py` 从磁盘读出。

## 没读出来的

- 类的真名。名字抹掉了,只能靠用途起名;上表里"我们的名字"是读代码后的命名,**不是**原名。
- `CollisionObject` 的另外两个子家族、依附体树的完整用途、502 个被动对象直接子类各自的专有逻辑。
- 受保护区域里的虚函数:有些虚表槽指向受保护的代码(按约定不碰),这些槽的语义只能从调用点推断。
