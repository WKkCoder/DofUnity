# `.ai` 决策树脚本

本文记录 `.ai` 的**语言结构**(证据 E-052)和**真假方向**(证据 E-053)。不含任何原版脚本内容或数值;关键字、函数名、编号、结构规则可以写,具体脚本里的值不写。判断的依据是客户端 `DNF.exe` 的只读静态读取和对全库 `.ai` 的统计,没有运行游戏。

## 它是什么

`.ai` 是怪物与 AI 角色的**决策树**:每次"思考"时从根结点出发,逐个判断条件,走到一个叶子,叶子给出一个返回值。全库 7,104 个,7,103 个是记号流(格式见 `docs/formats.md`),1 个不是。

- 一个怪物(`.mob`)或 AI 角色(`.aic`)的 `[ai pattern]` 段按难度列出若干路径,每个难度对应四个角色文件:事件(`event.ai`)、选目的地(`destinationselect.ai`)、动作(`action.ai`)、移动方式(`movemethod.ai`);少数目录里还有别的文件(`buff.ai`、`ai_pattern*.ai` 等)。客户端按"难度 → 文件向量"保存,`[import ai]` 按纯文件名在**同一难度**的向量里找。
- 四个角色文件共用同一种语言,返回值的含义由使用它的一方(事件、选目标、动作、移动)解释,脚本本身不带类型。
- 客户端里读取器是一个 C++ 类(类型描述符 `0x019f38e4`):加载函数 `0x008d1c00`,条件结点解析 `0x008d5090`,参数读取 `0x008d4e20`,求值循环 `0x008e01d0`,比较求值 `0x008dfd00`,关键字与 `[void]` 函数求值 `0x008d3930`。这些名字和地址都是我们自己的记录,不是原版的名字。

## 文法(已验证)

```
文件     ::= [ "[ai pattern]" ] ( think | "[return]" 值 | "[return str]" 名字 | "[import ai]" 文件名 )   (尾部的 [/ai pattern] 不读)
think    ::= "[think]" 条件 { 分支 } "[/think]"        至多两路分支,顺序随意
分支     ::= "[true]" 体 | "[false]" 体
体       ::= "[think]" … | "[return]" 值 | "[return str]" 名字 | "[import ai]" 文件名
条件     ::= 关键字 [ 运算符或函数名 ] 参数…
```

规则(客户端加载函数的读法,逐条在全库上核对过):

1. 控制标签只有 7 个,编号 0 到 6:`[think]`、`[/think]`、`[return]`、`[true]`、`[false]`、`[return str]`、`[import ai]`。关键字位置上标签和字符串记号**可以互换**(全库有 95 个 `[think]` 和 58 个 `[ai pattern]` 写成了字符串)。
2. 一个 `[think]` 只带**一个**条件;组合逻辑靠嵌套,没有 AND/OR。
3. 紧跟条件的 `[think]` 或 `[import ai]`(不写 `[true]`)算"真"分支;前者读完后外层再读一个标记当作自己的 `[/think]`,后者读完外层就结束。
4. 每个 `[think]` 读完两路分支后再读一个标记当作自己的 `[/think]`(不检查它是不是 `[/think]`);只写了一路分支时,读到 `[/think]` 就结束。**所以闭合标签多写了一个时,外层结点会提前结束,后面的内容原版读不到**——全库有几十个文件是这样的笔误(多数碰巧不影响结果,因为没读到的那一路本来就是 -1),我们按原样复现。认不出的控制标签(包括拼错的闭合标签 `[/thkink]` 之类)只是让当前结点结束。
5. 没写的分支返回 `-1`(结点创建时两路返回都初始化成 -1)。
6. `[return]` 后面是数字(整数、浮点都读成数)或名字;`[return str]` 后面必须是字符串。名字会在使用方的名表里查找,查不到客户端打"invalid key name"。

## 条件的编号与参数个数

条件结点存两个编号:**类型号**(哪个关键字)和**内部码**(怎么比较或怎么求值)。

- 类型号 0 到 7 是内置的:`[void]`(调函数)、`[mind]`、`[hp]`、`[mp]`、`[state]`、`[event]`、`[random]`、`[last result]`;0x08 到 0x3f 是 56 个关键字(表 A,见下)。`[stat change]`(0x0f)不是条件,而是**前缀**:读到它就再读一个关键字,真正的条件是后面那个。
- 关键字后是否写运算符,由类型号决定:`[target state]`、`[my state]`、`[hit]`、`[attack success]`、`[use skill]`、`[distance]`、`[casting]`、`[my death]`、`[target death]`、`[revive]`、`[overkill]`、`[attack type]`、`[attack condition]`、`[action after hit]`(14 个)固定用"等于";另有 29 个关键字有自己专用的内部码;其余(`[void]`、`[hp]`、`[mp]`、`[state]`、`[last result]`、`[target distance]`、`[my level]`、`[command]` 等)后面跟一个字符串当**运算符或函数名**。
- 运算符表 14 项,下标就是内部码:`check random()`、`check bonus random()`、`%>=`、`>=`、`==`、`is in range()`、`get random()`、`%==`、`%>`、`>`、`%<=`、`<=`、`%<`、`<`。其中 4 个是函数式写法;`%` 开头的是"按最大值的百分比比较"。
- 函数名表(`[void]` 用)14 项,内部码 0x0e 到 0x1b:`is target in attack area()`(4 个参数)、`..._box()`(6)、`..._surround()`(8)、`..._absolute()`(6)、`enemy number of in attack area()`(4)、`is the skill in cooltime()`(1)、`number of in attack area()`(7)、`party member number()`(0)、`is attack action enable()`(2)、`is custom action enable()`(2)、`damage check()`(1)、`is target object in area()`(7)、`is the load skill in cooltime()`(1)、`is free state()`(0)。
- 参数个数由内部码决定(`AiVocabulary.ParamCount`):0 到 8 个。参数是数字,或一个**名字**(见下)。`[check key cooltime]` 的参数是一个字符串键(在怪物的键名表里查下标),不是数字。`[my attack]` 读一个参数后内部码改成"等于"。

## 名字参数

`"all"`、`"monster"`、`"sit"` 这类写在参数位置的字符串不在代码里,而是数据文件 `AICharacter/OperatingValue.lst` 里的"名字 数值"对(客户端第一次需要时读入,最多 1000 对,同名只认第一次)。名字不在表里时客户端打"invalid parameter"。我们的 `AiConstants` 运行时从用户自己的数据包读这个文件,**仓库里不放它的内容**。全库的 `.ai` 里 2,240 个名字参数,除键名外都能在表里查到。

## 求值规则(观察,来自客户端求值函数)

- 每次"思考"前,客户端把一批现场值(自己与目标的状态、距离、HP/MP、地图、命令、事件标志)写进 64 个暂存槽,并把槽清成默认值;`[last result]` 读的是槽 7,由 `get random()` 和三个计数函数在**同一次求值内**写入,不跨帧。
- 求值循环:结点带"导入下标"时先换到那个脚本求值,返回它的结果,不判条件;否则求出条件值 0 或 1(大于 1 视为失败,返回 -1);有子结点就继续走,没有就返回这一路的叶子值。
- `get random()` 恒为真,把随机数写进槽 7;`check random()` 为真当随机数小于第一个参数;`%` 比较用浮点相除再乘 100。三个"区域内数量"类函数把个数写进槽 7 并恒为真,所以后面总是跟 `[last result]` 比较。
- 返回值的解释在使用方(事件、选目标、动作、移动)。这部分还没读完,见"未知"。

## 全库验证(`dnf ai-check`,证据 E-052)

C# 解析器 `Dnf.Game.Ai.AiParser`(`packages/com.dnfunity.game/Runtime/Ai/`,40 个合成数据测试)读全库:

- 7,104 个文件:1 个不是记号流;**7,100 个读通且没有错误**,4 个有错误——都是数据里的笔误(参数位置上写了奇怪的连接符、该写字符串键的地方写了数字、少了一个分支体),原版读它们同样会打日志。
- 23,747 个 `[think]` 结点,最大嵌套深度 25;7,079 个文件读完后还剩标记,其中 7,022 个剩的是 `[/ai pattern]`(原版不读它),其余 57 个是上面第 4 条说的多余闭合、尾部多写的 `[return]` 或结尾笔误。
- 整个文件的结果:嵌套 `[think]` 4,345、直接返回数值 2,750、导入 2、命名返回 1、空 6。

## 真假方向(证据 E-053)

大部分函数名字面就是"条件成立 = 真"。有歧义的是 `is the skill in cooltime()`:

- **汇编读法**(求值函数 `0x008d3930` 的 0x13 分支):技能表里找不到那个技能时返回 1(真);找到后调一个读"技能对象 +8 处受保护整数"的函数,读出值为 0 时返回 1,否则返回 0。那个函数的实现读不清,所以单看汇编不知道"值为 0"是不是"在冷却"。
- **语料读法**:在动作脚本里 4,925 个用到它的结点中,"真 → 返回 -1(不做)、假 → 返回非负数(去做)"的有 3,398 个(69%),"真 → 嵌套判断、假 → 返回非负数"的 956 个;反过来"真 → 非负、假 → -1"的前五名里一个都没有。作为对照,`is target in attack area()`(真 = 目标在范围内)的动作脚本里,"真 → 继续、假 → -1"的 1,164 个对"真 → -1、假 → 继续"的 199 个。再加上"技能不存在时返回真"只在"真 = 不可用"时才讲得通。
- **结论**:`is the skill in cooltime()` 为**真 = 冷却中或技能不存在(这次不能用)**,为假 = 可以用;`is the load skill in cooltime()` 同理。此前一份阅读笔记按汇编推断成反的,以语料为准。置信度:中高(统计差距很大,但没有读通受保护整数的含义)。

## 已知的未知

- 返回值的解释:四个角色(事件、选目标、动作、移动)各自怎样消费返回值、命名返回的名表从哪里来(`.mob` 里的哪个字段)。
- `check random()` 的精确分布、`[hit] 2`、`[stat change]` 前缀的求值含义、表 A 里语料中从未出现的 19 个关键字(`[warlike]` `[weapon type]` `[element]` `[casting]` 等)的具体语义。
- 动作返回后怎样启动 `.act`、每个角色一次思考的调用间隔(`.mob` 里的思考周期字段)。
- 受保护区域里的几处调用(角色路径的技能冷却判断等)按约定不碰,只能从使用方式推断。
