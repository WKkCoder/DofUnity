# 界面底栏与魔法值(E-087、E-088)

画面底部的原版界面(血球、魔法球、技能槽、菜单按钮)用用户自备图包里的 `sprite/interface2/hud/hud.img` 画出来,魔法值有了消耗与恢复。
本文只记**布局事实与规则**;图片本身不入库,运行时从用户自己的 `ImagePacks2` 里读。

证据等级:位置、层次是逐像素验证过的(高);液体取整、灰图标触发条件、魔法恢复速度的单位是推断(中、低),在对应段落里写明。

## 1. 怎么找到的

不新录像。用已有基线连拍(S07 普攻、S08 放技能)和 `dnf locate`:

```
dotnet src/Dnf.Cli/bin/Release/net10.0/dnf.dll locate --shot <基线截图.png> --min-opaque 40 --min-ratio 0.8 --top 400
```

它在全部 1575 个 NPK 的 570 万帧里找"不透明像素与截图逐像素相同"的帧并给出位置。一帧里就把底栏上的各个精灵都找到了,位置都是 **像素块左上角**(屏幕 800×600)。
自己渲染的画面(`combat-check --shots-at … --png …`)再用同一条命令找一遍,各精灵出现在同样的位置——这是实现与基线位置一致的自检。

## 2. 布局(`hud.img` 的帧号与屏幕位置)

| 部件 | 帧 | 位置(像素块左上角) | 说明 |

绘制顺序(从下到上):底栏 → 血球液体 → 魔法球液体 → 等级牌 → 菜单图标 → 菜单、商城按钮 → "I" 按钮 → 技能图标 → 热键字母。
依据:底栏在球的位置不透明,所以液体必须画在它上面;字母盖在图标上(基线里 A S D 字母压在图标右下角)。

**同一张字母条画了两次**:基线里 #45 整条在 (109, 579) 与 (268, 579) 各出现一次(各一组字母 100% 一致),其余部分被后画的菜单图标与按钮盖住。
我们直接把六个字母裁出来按各自位置画,效果相同。左边那组(从 x = 109 起、每格约 30 像素)看位置是物品快捷栏的热键字母(推断),没有物品,没做。

### 技能图标

`.skl` 的 `[icon] "图像" 帧 "图像" 帧`:第一个帧是能放时的亮图标,第二个是不能放时的灰图标。图包里的名字是 `sprite/` 加小写的图像名(例如 `Character/Swordman/Effect/SkillIcon.img` → `sprite/character/swordman/effect/skillicon.img`)。
基线 S07 里三个槽用的是第一个帧;S08 放鬼斩那一刻,S、D 两个槽(没有在冷却)也显示灰图标——**"主角正在施法时其它槽也变灰"**。
我们现在只在"冷却中或魔法不够"时变灰(推断),施法期间的变灰没做。

### 液体

液体帧是 56×56 的圆;不满时露出下面若干行,上面是底栏的暗色底座。行数取 `⌈56 × 比例⌉`,还有血就至少 1 行,满格取整张。
基线只能量到整行(见 §4),向上还是向下取整没有样本——**推断**。

## 3. 实现

- `SkillDef`:读 `[icon]`,四个属性 `IconImage`、`IconFrame`、`IconDisabledImage`、`IconDisabledFrame`;形状不对当作没有。
- `HudArt`(`Dnf.Play`):`For(assets)` 按图包共用一份(副本每换一个房间就新建战斗会话,共用才不会重复裁液体、让 GPU 端的贴图越攒越多);`Build` 按上面的顺序把精灵加进绘制列表。
  液体按行数裁帧并缓存(每个球最多 56 个帧);缺底栏、液体或字母条任何一个就不创建。
- `RoomCombatSession`:有原版底栏就用它,没有(合成数据的测试、图包不全)退回占位的色块血条;"DEAD" 字样两种都有。
- 所有精灵走原来的叠加层管线(`OverlayArt.Place`,界面层),CPU 合成与 GPU 都不需要新特性。

没做:经验条与疲劳条、状态图标、物品快捷栏与数字、技能等级小字与冷却遮罩、`SP` 数字、球上的高光、鼠标悬停与点击、右上角小地图与怪物血条(这两个仍是占位)。

## 4. 魔法值(E-087)

### 观察(基线液面粗测,不新录)

用 `orb_level.py`(非 REA,本机脚本,不入库)在已有 S08、S08b 连拍里逐行数魔法球液体帧与截图一致的行数(满格 56 行):

- 放鬼斩的那一刻魔法球液面下降约 4 行;放上挑下降约 1 行。
- 之后 2 到 3 秒的窗口里回升 0 到 1 行。
- 两次下降的比例与 `.skl` 里两个技能 `[consume MP]` 的比例相符(同一个魔法上限能同时解释两者)。

### 规则(推断,客户端的扣蓝与回蓝代码没读到)

- 技能真正开始的那一刻扣 `[consume MP]`(按技能等级在 `.skl` 的两个数之间线性插值,`HeroSkillSlot.ConsumeMp`)。魔法不够就放不出来,不启动冷却、不扣蓝(`SkillCastResult.NoMp`)。
  检查顺序:没绑定 → 没实现 → 冷却 → 魔法 → 此刻能否开始(忙不扣蓝)→ 扣蓝并起冷却。
- `.chr` 的 `[MP regen speed]` 按"每分钟点数"解释:只有这个单位下"几秒内回升不到 1 行"才对得上;按每秒或每 5 秒解释,几秒内会回升好几行,与基线的 0 到 1 行对不上。
  **每 30 秒也勉强说得通,粗测区分不开**——所以这个单位的置信度只有中低。
- 恢复是连续的:每步加"速度 × 毫秒",攒够 1 点才加到魔法值;累加器的单位是"点 × 60000",很多小步累加不产生浮点误差;满了清零;主角死了不恢复。
  墙钟时间,不受命中停顿影响(与冷却同样的假设)。
- 换房间带着当前值与累加余量(`HeroVitals.CopyStateFrom`)。

### 没做 / 没弄清

- 客户端扣蓝与回蓝的代码没找到;恢复是连续的还是按固定节拍加点,没验证。
- 施法、受击、倒地期间恢复是否暂停,没验证。
- 魔法上限与恢复速度只取 `.chr` 第 1 级的初始值(成长类型与装备怎么叠加还没做)。
- 魔法不足时的提示与音效。
- 不带生命值对象的无伤害模式(`--no-damage`、`nodamage`)里没有魔法值,也没有底栏。
