## 3. 读法与局限

- **客户端认识 / 服务端认识**:这个标签的字符串出现在对应二进制里(E-019、E-043)。说明那边有函数认识它,**不说明语义已知**;服务端是带符号的二进制,所以常用来指路(哪个加载函数读它),客户端的 `.act`、`.ai`、`.ptl`、`.key` 只有客户端认识。
- **加载器读入**:静态扫描 `CONSUMERS`(`tools/py/coverage.py` 开头的对照表)列出的源文件里写成 `"[标签]"` 的字符串字面量,并且这个标签在这类脚本的目录里出现过。**读入只说明标签被识别并存进了数据结构,不等于玩法里已经生效**(例如 `.atk` 读到的击退、浮空、属性,有的已经接进受击反应,有的还没有)。误差两个方向都有:靠默认值处理而没写出字面量的会被记成没读,字面量写了却没真正用上的会被记成读了。
- **仅语法层**:`.act` 的语法树(`ActParser`,E-050)与 `.ai` 的词表和解析器(`AiVocabulary`/`AiParser`,E-052)读通了全部文件,但动作状态机与怪物 AI 求值这两个运行时还没有做;它们的标签只算"认得结构"。
- **独立核对**:这类脚本有没有"另一份独立实现或原版机器码"的整库对拍,结果在表 5。没有这一格的类型,读法只有合成数据的单元测试。
- **出现次数加权**让 `.equ`(装备与物品,68,499 个文件)占一半以上,所以"全部"一行的百分比看起来很低;`.equ` 里目前只读了换装图层这一小块。已接入的类型一行更能反映"玩法切片里用到的脚本读得怎样"。
- **台账引用检查**只检查编号存在,不检查编号的内容与代码是否相符。
- 表 5 的"逐技能扫描"是记录项,不计入"全部通过":没跑完的状态是没进入(条件不满足)或超时,不等于行为错误;它说明原版 Squirrel 状态脚本不改动就能被我们的虚拟机与接口跑完多少,**不等于行为与原版一致**。
- **没放进 `verify-all.sh` 的**:Unity 里的 CPU 与 GPU 逐字节对拍(`tools/unity-build-town.sh macos`,约 6 分钟,最近一次 45 帧零差异)、EditMode 测试(`tools/unity-test.sh EditMode`)、整局实时运行;它们需要构建 Unity 播放器,结果记在对应里程碑的台账行里。

## 4. 从表格读出的缺口(按出现次数排序)

1. **`.equ`(55.9%)**:装备与物品的属性几乎没读(只读了换装图层)。这是"角色面板、装备、掉落"的数据来源,量最大;但对"击杀与结算"这条切片不是必需。
2. **`.act`(14.3%)**:动作状态机(`[TRIGGER]`、`[BEHAVIOR]`、`[DO BEHAVIOR]` 等)语法层读通,运行时没有。怪物出招现在是按 `.mob` 与 `.atk` 的直接数据实现的 v0,不是跑 `.act`。这是最大的"逆向 + 重写"缺口。
3. **`.stk`(6.1%)、`.qst`(1.9%)、`.ptl`(1.6%)、`.key`、`.aic`**:没有加载器(物品、任务、粒子、按键触发器、AI 角色);`.ptl` 是特效的粒子,画面上会缺。
4. **`.ai`(3.9%)**:词表与解析器有,求值没有;怪物现在用默认出招节奏。
5. **`.chr`**:读入 50.6%(按次数),没读的 `[physical attack]`、`[magical attack]`、`[module damage rate]` 正是真实伤害流水线的输入之一,下一步先看它们的结构。
6. **Squirrel 接口**:表 3 里 Inferred 占约 45% 的调用点,按调用次数从高到低核对(`sq_IntVectPush` 起)能最快提高技能行为的可信度。

## 5. 缺口清单

### 5.1 复现

```

```

`verify-all.sh --only atk,act` / `--skip oracle` 可以只跑一部分(名字见 `tools/py/verify_all.py` 开头)。需要的本机输入(都不入库):`out/tag_catalog.json`(`tools/py/tag_catalog.py`)、`re/notes/strings_decoded.tsv`(客户端标签字符串)、`re/ghidra/out/server_tag_refs.tsv`(服务端标签字符串);`oracle` 一项还需要 `re/venv` 里的 Unicorn 与本机的服务端二进制。

### 5.2 对照表要随加载器更新

新增或移动加载器源文件后,改 `tools/py/coverage.py` 开头的 `CONSUMERS`(哪个文件读哪类脚本、是读入还是只做语法),再重新生成。

### 5.3 追溯性的局限与下一步

- 文件级引用是最低要求。更细的做法是把"规则 → 证据编号"写进测试名或注释(已有大量这样的写法,例如 `AttackInfoLoaderTests`、`MonsterDamageTests`),新写的代码照此办。
- 台账里 E-026、E-040 没有被代码或文档引用(它们是早期的探查结论,没有对应的实现);不是错误,只是提醒。
- 表 4 不检查证据的"类型":规则是**观察**(读到的字节与跑出的结果)还是**推断**(猜的)要看各台账行与文档里的标注,代码里凡是推断或占位的地方都应当注明,新增时同样要求。
